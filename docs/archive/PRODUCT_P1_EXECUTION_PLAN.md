## 2. P1 产品目标

### 2.1 目标一句话

让平台从“可以浏览和发布”升级为“有审核、有个人资产、有互动反馈”的可运营产品。

### 2.2 P1 完成后平台应该具备的能力

- 用户发布项目后，不再直接公开，而是进入审核流程。
- 用户可以在个人中心看到自己的资料、发布记录、收藏记录和项目状态。
- 平台可以统计项目浏览、收藏、点赞，并用于后续推荐和趋势能力。
- 后台可以高效处理待审核项目，并控制展示状态。

### 2.3 P1 的核心闭环

```text
游客浏览项目
  -> 登录 / 注册
  -> 发布项目
  -> 项目进入待审核
  -> 管理员审核通过
  -> 项目公开展示
  -> 其他用户浏览 / 收藏 / 点赞
  -> 作者在个人中心看到反馈数据
```

P1 不建议一上来大拆，但建议做“兼容式演进”。

## 4.1 `projects` 表扩展建议

当前 `projects` 已有：

- `id`
- `title`
- `description`
- `category_id`
- `cover_image`
- `creator_user_id`
- `status`
- `sort_order`
- `created_at`

建议扩展为：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `summary` | `VARCHAR(255)` | 一句话简介，首页和列表使用 |
| `content` | `TEXT` | 项目详细内容 |
| `audit_status` | `VARCHAR(20)` | 审核状态：`pending` `approved` `rejected` |
| `audit_comment` | `VARCHAR(255)` | 驳回原因或审核备注 |
| `audited_by` | `INT` | 审核管理员 ID |
| `audited_at` | `DATETIME` | 审核时间 |
| `published_at` | `DATETIME` | 真正公开时间 |
| `view_count` | `INT` | 浏览量冗余统计 |
| `favorite_count` | `INT` | 收藏量冗余统计 |
| `like_count` | `INT` | 点赞量冗余统计 |
| `updated_at` | `DATETIME` | 更新时间 |

### P1 推荐状态规则

- `status`
  - 保留现有字段，用于内容可见性，例如 `draft` / `published` / `hidden`
- `audit_status`
  - 新增审核维度，用于审核流程，例如 `pending` / `approved` / `rejected`

推荐组合逻辑：

- 用户刚发布：`status = draft`，`audit_status = pending`
- 审核通过并上线：`status = published`，`audit_status = approved`
- 审核驳回：`status = draft`，`audit_status = rejected`
- 后台人工下线：`status = hidden`，`audit_status = approved`

## 9. 技术实现建议

## 9.1 尽量少改但要留扩展位

P1 不建议重构成复杂 DDD，只要做到：

- 表结构可扩展
- 接口边界清晰
- 页面入口合理
- 数据统计可持续累积

## 9.2 冗余计数策略

对于 `view_count`、`favorite_count`、`like_count`，建议采用：

- 明细表做真实记录
- 项目表做冗余计数

这样可以兼顾：

- 查询快
- 后续可重算
- 趋势和榜单容易做

## 9.3 审核流建议

审核相关不要只改 `status`，要同时保留审核日志，否则后续无法追踪。

## 9.4 浏览统计建议

浏览量不要每次刷新都无脑加 1，建议：

- 登录用户：同一用户同一项目 30 分钟内只记一次
- 游客：按 `visitor_key + project_id` 做时间窗口去重

## 10. 风险与注意事项

### 10.1 审核状态和展示状态容易混淆

必须明确：

- 审核状态控制“是否通过审核”
- 展示状态控制“是否对外展示”

### 10.2 个人中心不要做成纯信息页

重点不是展示资料，而是让用户看到：

- 我发了什么
- 现在处于什么状态
- 收到了多少反馈

### 10.3 互动数据需要防刷

P1 可以先做轻量风控，但必须至少保留：

- 登录校验
- 唯一关系约束
- 浏览去重策略

## 11. 结论与建议

如果你现在直接开干，我建议就按下面顺序推进：

1. 先改数据库和后端接口，完成审核流底座
2. 再改 Admin 项目管理，让审核真正能跑起来
3. 接着补个人中心，让用户看到自己的资产
4. 最后接收藏 / 浏览 / 点赞，把闭环补完整

这个顺序的好处是：

- 不会先做出“看起来完整，但后台没法运营”的壳子
- 每一步都能独立验收
- 做完 Sprint 1 就已经开始产生平台治理能力

1. 用户登录后提交项目
2. 项目进入 `pending`
3. 首页不直接公开
4. 管理员后台审核
5. 审核通过后进入公开展示
6. 驳回时作者可查看驳回原因
